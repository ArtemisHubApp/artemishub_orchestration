# Plano 3: repo `ArtemisHubApp/.github` (formulários, template de PR, labels e CODEOWNERS)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** um repo `ArtemisHubApp/.github` que dá a todos os repos da org os mesmos formulários de issue, o mesmo template de PR e as mesmas labels, e um CODEOWNERS de exemplo para o time preencher.

**Architecture:** o GitHub usa os arquivos de `ISSUE_TEMPLATE/` e o `pull_request_template.md` do repo público `.github` da org em todo repo que não tem os seus próprios (nenhum dos 5 tem hoje). As labels não são herdadas: o `scripts/labels.py` (só biblioteca padrão) compara as labels de cada repo com a lista padrão e cria ou atualiza o que falta via `gh`, nunca apaga. O repo usa o mesmo CI reutilizável dos repos filhos (`python-ci.yml@main`), com pytest validando os YAML dos formulários contra a lista de labels e de repos do `labels.py`.

**Tech Stack:** GitHub issue forms (YAML), Markdown, Python 3.11+ (stdlib no script; `pytest`, `pyyaml` e `ruff` só no grupo dev), uv, `gh` CLI.

**Spec:** `docs/superpowers/specs/2026-11-17-artemishub-orchestration-design.md`, seção 6.11 (e 6.12 item 3 para o checklist). ADR-009 no `artemishub_docs`. Índice: `docs/superpowers/plans/2026-11-17-00-indice.md`. Issue: `ArtemisHubApp/artemishub_orchestration#4`.

## Decisões deste plano

1. **O `labels.py` mora no repo `.github`, não no orquestrador.** Assim os testes do `.github` conferem que toda label citada num formulário existe na lista padrão (Review Focus 1), sem duplicar a lista em dois repos. Quem roda é só quem tem permissão de *maintain*, a partir de um clone do `.github`.
2. **CODEOWNERS não é herdado da org** (limitação do GitHub: ele só vale dentro de cada repo). O `.github` guarda `exemplos/CODEOWNERS`, todo comentado. Cada repo copia para o próprio `.github/CODEOWNERS` quando o time definir as donas.
3. **Branch de trabalho no `.github` vai para `main`**, porque o repo nasce sem `staging`. O Plano 5 decide se o `.github` ganha `staging` (o GitHub lê os templates da branch padrão).
4. **Semanas: `semana-1` a `semana-10`** (`SEMANAS = 10`). As labels atuais vão até `semana-7`; ajuste a constante se o roadmap tiver outro tamanho, antes do `--apply`.
5. **Issue em branco desligada** (`blank_issues_enabled: false`): toda issue nasce de um formulário, que já pede Semana, Critérios de aceite e Repo afetado.

## Global Constraints

- Org: `ArtemisHubApp`. Repo novo: `ArtemisHubApp/.github`, **público** (senão o GitHub não usa os templates nos outros repos).
- Repos alvo, nesta ordem (é a lista `REPOS` do `labels.py` e as opções de *Repo afetado*): `artemishub_orchestration`, `artemishub_docs`, `artemishub_frontend`, `artemishub_backend`, `artemishub_agents`, `artemishub_rag`, `.github`.
- Labels padrão (nome, cor, descrição), exatamente:
  - `semana-N` para N de 1 a `SEMANAS`: cor `bfd4f2`, descrição `Roadmap: semana N`.
  - `prioridade: alta` `b60205` `Caminho crítico ou entregável do roadmap`
  - `prioridade: média` `fbca04` `Importante, mas não bloqueia outras tarefas`
  - `prioridade: baixa` `0e8a16` `Desejável; pode ficar para depois`
  - `tipo: feature` `a2eeef` `Funcionalidade nova ou mudança de comportamento`
  - `tipo: bug` `d73a4a` `Algo não funciona como deveria`
  - `tipo: chore` `c5def5` `Manutenção, configuração ou faxina, sem mudar comportamento`
  - `tipo: docs` `0075ca` `Documentação`
- Cor em 6 dígitos hexadecimais minúsculos, sem `#`. Descrição com no máximo 100 caracteres (limite do GitHub).
- `labels.py`: só biblioteca padrão; ensaio por padrão, muda algo só com `--apply`; **nunca apaga label**.
- Formulários: `feature.yml`, `bug.yml`, `chore.yml`, `docs.yml` em `.github/ISSUE_TEMPLATE/`. Prefixo de título `feat: `, `fix: `, `chore: `, `docs: ` (Conventional Commits). Labels fixas `tipo: feature`, `tipo: bug`, `tipo: chore`, `tipo: docs`. Os quatro têm os campos com `id` `semana` (dropdown, obrigatório), `criterios` (textarea, obrigatório) e `repo` (dropdown, `multiple: true`, obrigatório).
- Opções de `semana`: `Semana 1` … `Semana 10` e, por último, `Backlog (sem semana)`.
- Texto em português. Commits e título de PR em Conventional Commits.
- Ações que mudam a org (criar o repo, `labels.py --apply`, merge) pedem confirmação da Amanda na hora.

## Review Focus

1. **Label de formulário que não existe no repo:** o GitHub ignora em silêncio a label `tipo: …` se ela não existir no repo onde a issue é aberta. O teste `test_labels_dos_formularios_estao_no_padrao` (Task 3) garante que estão na lista padrão, e a Task 5 roda o `labels.py --apply` antes de conferir os formulários.
2. **Label já existente com outra cor ou outra caixa** (`semana-4` está `0E8A16` no `rag` e `ededed` no `docs`; `Semana-4` contra `semana-4`): o script tem de atualizar, e não tentar criar (o `gh label create` falharia com "already exists"). Testes `test_planejar_atualiza_cor_ou_descricao_diferente` e `test_planejar_casa_nome_sem_diferenciar_maiusculas` (Task 1).
3. **Sem permissão num repo** (403 do `gh`): o script segue para os outros repos, avisa qual falhou e sai com código 1, sem traceback. Teste `test_main_continua_quando_um_repo_falha` (Task 2).
4. **Rodar sem flag não muda nada:** quem roda para "ver" não pode alterar labels. Teste `test_main_sem_apply_so_lista` (Task 2).
5. **Repo filho com `ISSUE_TEMPLATE` próprio** esconde os da org naquele repo. Não dá para testar aqui; o README do `.github` avisa, e a Task 5 confere os 5 repos com o comando de lá.

### Task 2: CLI do `labels.py` (ensaio, `--apply`, `--repo`)

**Files:**

**Interfaces:**
- Consumes: `labels_padrao`, `planejar`, `comando_gh`, `REPOS`, `ORG` (Task 1).
- Produces:
  - `Gh = Callable[[list[str]], str]`: recebe os argumentos do `gh` (sem o `"gh"`) e devolve o stdout; falha com `RuntimeError(mensagem)`.
  - `rodar_gh(args: list[str]) -> str`: `subprocess.run(["gh", *args], capture_output=True, text=True, encoding="utf-8", timeout=60)`; `returncode != 0` ou `OSError`/`TimeoutExpired` viram `RuntimeError` com o stderr.
  - `listar(repo: str, gh: Gh) -> list[dict[str, str]]`: `gh label list -R <repo> --limit 200 --json name,color,description`, com `json.loads`.
  - `sincronizar(repos: list[str], aplicar: bool, gh: Gh) -> int`: para cada repo imprime `== <repo>` e uma linha por mudança (`criar semana-8`, `atualizar semana-4 (era Semana-4)`) ou `sem mudanças`; com `aplicar`, roda `comando_gh` de cada uma. Um `RuntimeError` num repo imprime `ERRO <repo>: <mensagem>` em stderr e passa ao próximo. Devolve 1 se algum repo falhou, senão 0. Sem `aplicar`, termina com `Ensaio: nada foi alterado. Rode com --apply para aplicar.`
  - `main(argv: list[str] | None = None, gh: Gh = rodar_gh) -> int`: `argparse` com `--apply` e `--repo NOME` (repetível; aceita só nomes de `REPOS`, senão `parser.error`). Antes de tudo, se `gh is rodar_gh and shutil.which("gh") is None`, imprime `ERRO: gh não foi encontrado no PATH. Instale em https://cli.github.com e rode gh auth login.` e devolve 1. Repos viram `f"{ORG}/{nome}"`. `if __name__ == "__main__": raise SystemExit(main())`.
